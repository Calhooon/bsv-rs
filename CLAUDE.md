# CLAUDE.md: bsv-rs

The working rules for this crate. `README.md` is the guide for users (what it is, the examples, the contracts, the numbers); this file is for whoever changes it. Read both, then the module's own `CLAUDE.md` (28 of them under `src/`, 31 with `tests/` and `benches/`) before touching that module.

## What this crate is, in one paragraph

A reference-parity port of the TypeScript `@bsv/sdk` (`~/bsv/ts-sdk`; the `ts-stack` monorepo at `~/bsv/ts-stack` carries the newer packages and the conformance corpus), cross-checked against the Go SDK (`~/bsv/go-sdk`). Fourteen feature-gated modules in dependency order (`primitives → {script, block} → transaction → wallet → {messages, auth, overlay} → {storage, registry, kvstore, identity}`; `compat` and `totp` stand on `primitives`), one `Error` enum (`src/error.rs`, `Clone + PartialEq + Eq` so tests assert on it), and every public behavior pinned by a test that fails when the behavior changes. It ships to crates.io as `bsv-rs` and runs on native and `wasm32-unknown-unknown` (Cloudflare Workers are the production target: the LOW stack's overlay engine, watchtower, relay, app-layer and monitor).

## Rules

1. **The reference decides.** Before writing or changing a wire format, a verdict, a derivation or an error text, read the TypeScript implementation first (`~/bsv/ts-sdk/src/...`; for overlay/auth transports also `~/bsv/ts-stack/packages/...`), then Go. Conform. If you cannot conform, the divergence is a STATED FINDING: a `### Notes: cross-SDK parity` paragraph in the `CHANGELOG.md` entry and a line in the list below, never a silent difference. A reference bug you do not follow is recorded the same way (the TOTP digits, the nonce HMAC inputs, the Go admin-token key).
2. **Every fix lands with a test that was RED before it.** Watch it fail on the pre-fix code (a scratch copy with the fix removed, never a `git checkout` of a dirty tree), then green. Regression tests name the finding in their function name (`a_deep_diamond_chain_links_and_verifies_in_linear_time`, `an_unproven_spend_creating_satoshis_is_refused`). A fixture the test needs is built by this crate's own writer, so it cannot drift from the wire format.
3. **Vectors are the source of truth.** `tests/vectors/*.json` are shared byte-for-byte with the other SDKs: never edit one to make a test pass. The `ts-stack` corpus (`$BSV_CONFORMANCE_DIR`, default `../ts-stack/conformance`) is read, not copied; a vector this crate cannot express is counted in the enumerated `unsupported` allowlist with its reason, and the class totals are pinned (`tests/conformance_scripts.rs`, `tests/conformance_beef.rs`). A total that moves is a finding.
4. **Tests are hermetic.** No test may depend on the network being present OR absent. A test that needs an overlay failure injects a resolver that cannot succeed (`GlobalKVStore::with_resolver`, `LookupResolverConfig { host_overrides, facilitator, .. }`); a test that needs an HTTP answer uses `wiremock`. Five kvstore tests once asserted an error "because there are no live SLAP hosts" and failed on every machine with a route to them (0.3.24).
5. **Nothing panics on input.** Parsers bound every pre-allocation by the bytes remaining (`primitives::bounded_capacity`), index with `get`, and return `Err` on a bad count; on wasm32 a panic is an abort nobody can catch. The interpreter's budgets are errors of their own class (`ScriptResourceLimit`), never a hidden allocation. `cargo fuzz run <target>` on any parser you touch.
6. **wasm32 is a build target of every change.** `cargo build --target wasm32-unknown-unknown --no-default-features --features "auth,wallet,transaction,overlay,socketio,wasm"` must pass. `http` is not in the slice: it is native-only (reqwest's futures are not `Send` on wasm32, its wasm backend has no `ClientBuilder::timeout`), no Worker asks for it (`docs/DEPENDENTS.md`), and `build.rs` refuses it on wasm32 with one message (#152); a consumer that asks for it reopens #152 as the fix. No `std::time::SystemTime` (use `crate::util` time helpers), no `thread::spawn`, no tokio time driver outside `#[cfg(not(target_arch = "wasm32"))]`; a new dependency behind a feature must not break a wasm build of a sibling feature (the `socketio` rule).
7. **Clippy is `-D warnings`, rustfmt is law, doc tests compile.** `cargo clippy --all-targets --all-features -- -D warnings`, `cargo fmt --check`, `cargo test --doc --all-features`, `cargo build --examples --all-features`, `cargo test --test readme_examples` all green before a push. A pull request and a push to `beta` or `main` run exactly the required set of the line's protection (the Linux stable cell, the combined wasm32 slice, `dependents` on `main` alone; a push less `semver` and `beta-born`, which read a pull request); a dispatch of `ci.yml` (the nightly's, the sync's) and a tag's call run the whole test matrix (Linux, macOS, Windows × stable, beta) and `dependents` on either line; the jobs that judge something other than the commit run on dispatch and before every tag, each in its own workflow (`bench.yml`, `msrv.yml`, `features.yml` with the other five wasm32 slices, `machete.yml`, `docs.yml`; `tests/arch_ci_pr_runs_the_required_set.rs`; the owner's word of 2026-10-27).
8. **The README's code is the examples.** Every ```rust block in `README.md` that opens with `// examples/<name>.rs` equals that file's body; `tests/readme_examples.rs` pins the bytes. Change the example, run it, paste it. Never write a README snippet that is not a compiled example.
9. **Semver within 0.3 is additive.** A new public field on a struct that downstreams build with a literal (`ScriptEvaluationError.resource_limit` in 0.3.23) is called out in the changelog with the one-line migration. Yank a release that was wrong (0.3.21 was; the changelog says so and why).
10. **A release is a ritual, not a habit.** `Cargo.toml` version, a `CHANGELOG.md` entry (what changed, why it was wrong, which test pins it, the parity note if any), `cargo publish` (credentials live in `~/.cargo/credentials.toml`, never in the tree), tag `vX.Y.Z`, push `main` and the tag. Downstreams pin `"0.3"` and pick a patch up on their next `cargo update -p bsv-rs`; a `[patch.crates-io]` to a DIFFERENT version is silently unused until that update (cargo warns; read the warning). Every fix is born on `beta`; `main` takes a `git cherry-pick -x` of it in four classes only (`beta-born` checks), and the sync PR picks main's commits back onto `beta` (`main-in-beta` checks; `RELEASING.md`, "The direction rule").

## The contracts (the short form; the README has the long one)

- `Spend` = the TS default evaluation mode without a word (strict for version ≤ 1: MINIMALDATA, LOW_S, CLEANSTACK, NULLDUMMY; relaxed for version ≥ 2; push-only always; no NULLFAIL), or, with `set_flags`, the NODE's word: `ScriptFlags::block(era)` (consensus) / `ScriptFlags::standard(era)` (mempool policy), every rule at bitcoin-sv v1.2.2's site under its version gate (`src/script/flags.rs` carries the table and the citations; the reference clone is `~/bsv/bitcoin-sv` at `v1.2.2`, `879fc8b`). A consensus oracle selects the block word. Post-Genesis opcodes, plus the Chronicle ones for a post-Chronicle UTXO (the word's `UTXO_AFTER_CHRONICLE`, or version > 1 by default); an undefined opcode executed, a truncated push reached, a second OP_ELSE are failures in every mode; a FORKID signature's push stays in the scriptCode (0.3.27, bsv-rs#12). The combined-script CHECKSIG subscript; in the default mode `memory_limit: None` uncapped, as the reference's `Spend` is (#331, the keeper's ruling of 2026-10-27), a budget the caller's `Some(n)` per stack, an allocation the allocator refuses a decline, never an abort, the 1 GiB element bound at a push, `OP_CAT`, `OP_NUM2BIN` and `OP_LSHIFTNUM`, and at an arithmetic result a decline judged from the operands' bytes before the arithmetic, the step's peak asked of the allocator first in every mode (#374: 6 times the operands' bytes for `OP_MUL`, 12 for `OP_DIV` and `OP_MOD`, 2 for the rest, a number's read and the numeric shifts the same); in the default mode an operand whose magnitude passes 536,870,888 bits (a minimal encoding past 67,108,862 bytes) is invalid at its read in the reference's words, `Invalid string length`, a verdict (V8's longest string at the reference's pin, not a BRC rule; the node's number length after Chronicle is 32,000,000 bytes, so the reference reads numbers the node refuses and the default mode follows it; the keeper's word of 2026-10-27, `src/script/spend/reference_read.rs`), and so is a result past the figure at its push where the reference builds it through `toString(2)` (`OP_ADD`, `OP_SUB`, `OP_1ADD`, `OP_1SUB`, `BigNumber.ts:771-781`; `OP_LSHIFTNUM`, `Spend.ts:1066`; there an uncaught `RangeError` out of its `verify`, here a verdict in its words after a caller's budget's decline, the keeper's word of 21:5xZ; `OP_MUL`'s and `OP_2MUL`'s pushed, as `mul` writes no string); `Transaction::verify` takes the caller's budget as the reference's third parameter, `None` uncapped as the reference's default; under a word the node's count (one budget over both stacks, 32 bytes per element, 100 MB by default, the mempool path's policy a verdict, `OP_NUM2BIN`'s size bounded by `INT32_MAX`; 0.3.30, bsv-rs#30); on the block path a node's budget is its operator's mandatory `-maxstackmemoryusageconsensus` (0 = `INT64_MAX`), no constant: `Spend::set_stack_memory_consensus` is that node's verdict (#38), `memory_limit: Some(X)` only a decline above `X`, `Some(usize::MAX)` a node run with 0; `ScriptResourceLimit` as its own error class, a decline an embedder never reads as invalid, `Transaction::verify` included (`Error::ScriptEvaluationDeclined`, #38); every refusal of the budget before the allocation it would need. Consensus and policy are different things and this crate says which is which: a rule that is policy is never enforced under the block word.
- BEEF: linear linking (one full link per distinct parent, stubs after), `verify` by txid (proven: tracker, not descended; unproven: every input script executed, outputs ≤ inputs), cycles terminate, the merkle path reattached on `from_beef`; valid whatever its order on the wire (#240): the whole path sorts before judging, the stream defers a child by its index entry until its parent, under no bound, and folds a released one per step under the caller's budget; whether BRC-62's order is normative is upstream as BRCs #359.
- Sighash lives in the templates; `SigningContext::compute_sighash` signs the digest the node's `SignatureHash` dispatches to (`compute_sighash_dispatched_for_signing`, the interpreter's; the SINGLE sentinel `one` kept), its scriptCode the locking script unless `with_script_code` names another (`chronicle_unlocking_script_code` for a CHECKSIG in a post-Chronicle unlocking script; 0.7.0); `SighashCache` for midstate reuse; RFC 6979 via k256 (k256 0.14 signs a digest at or above n with the bytes `@bsv/sdk` 2.0.16 and go-sdk produce, derived with both on 2026-10-24; k256 0.13 did not, and the pin of that regime moved with #125).
- Auth: BRC-103 (the code's older comments say BRC-31: the same protocol under its earlier name); nonces are the canonical 48-byte form since 0.3.6 (the 32-byte legacy accept window is still in place; remove it deliberately, with a changelog line).
- Overlay: request coalescing (`tokio::sync::watch`) and host reputation are this crate's additions over the reference (documented, not divergences: the wire is the reference's).

## Known cross-SDK divergences (keep this list honest)

- Raw base58 rejects empty input and surrounding whitespace, as TS does;
  bitcoin-sv@6504a3af `src/base58.cpp:25-79` accepts them. The node's checksum
  and 50 key vectors pass in `tests/chain_encoding.rs`.
- Varint readers are canonical from 0.6.0, as node and TS strict readers are;
  go-sdk@v1.7.1 `util/varint.go:71-105` remains lenient. Legacy callers can
  use `read_var_int_lenient`; node size bounds use the CompactSize methods.
- The wallet wire's optional varints are TS's and Go's plain form (0.9, #149);
  a listOutputs `offset` below `-1`, which TS writes in two's complement and
  its own processor reads as absent, is refused at this crate's writer.

- Go defaults `counterparty` to `Anyone` in `create_signature`; Rust and TS use `Self_`.
- BRC-56 HMAC key (`5119a9b` `wallet/0056.md:66,73`): this crate keys the HMAC with the shared X coordinate as 32 bytes, as Go (`primitives/ec/symmetric.go:82-90`), Python and rs-sdk; ts-sdk drops its leading zero bytes (`ts-stack@edf6e03` `packages/sdk/src/wallet/KeyDeriver.ts:270`), a different tag for one key in 256. `verify_hmac` accepts the 32-byte tag only and refuses the minimal-length one as `Error::HmacMinimalLengthKey` (#148).
- Go lacks TOTP, overlay caching/historian/reputation, and the RPuzzle template.
- TS TOTP defaults to 2 digits; this crate uses 6 (RFC 6238).
- TS and Go disagree on the nonce HMAC inputs (`protocolID [2,'server hmac']` + UTF-8 keyID vs security level 1 + raw-bytes keyID); this crate follows Go's level with its own base64 keyID. `verify_nonce` is only ever called on a peer's own nonces, so nothing crosses the gap in practice.
- `Peer` verifies an initial response and a general message on both `start` paths in the reference's order and words (#353); three words differ (a `ProtoWallet`'s nonce miss reaches the Peer's words here, where the reference's `verifyHmac` throws `HMAC is not valid` first; a general message without a nonce is refused by the Peer here, by the reference's message snapshot there), and three of the reference's checks are not here: the replay claim of each message nonce (#362; `Peer.ts:258-272`, Go's `claimMessageNonce`), the `yourNonce` and identity checks of a certificate request and response (#363), and the general message's wait for a session's pending certificate validation (#364; `Peer.ts:1318-1325`; `certificates_validated` is never set here). One refusal is in other words (an HTTP response without the auth headers is the transport's refusal in the reference's words since #354, `SimplifiedFetchTransport.ts:220-232`): an absent `yourNonce`, refused by the reference's message snapshot (`Peer.ts:767`), is refused here by the nonce check. Go does not compare an initial response's identity with the pinned one (`auth/peer.go:680` at `2ca481c`); this crate and TS refuse it.
- Go signs overlay admin tokens with `counterparty = Self` (a different signing key); this crate matches the deployed TS validators (`@bsv/sdk 1.10.1`).
- TS's explicit `verifyFlags` applies a flag as given (NULLDUMMY, MINIMALDATA, LOW_S, CLEANSTACK at every version; no `CHRONICLE` flag); this crate's `set_flags` applies the node's version gate at the node's sites (0.3.26). The default mode keeps TS's no-NULLFAIL; the block word carries it.
- TS's default keeps a lenient parser (a truncated push is a shorter push), allows a second OP_ELSE outside explicit flags, and deletes every signature from the scriptCode; this crate follows the node in every mode (0.3.27, bsv-rs#12). TS's `OP_SUBSTR`/`OP_LEFT`/`OP_RIGHT` names sit at `0xb3`-`0xb5`; this crate's constants of those names are the legacy `0x7f`-`0x81`, and `0xb3`-`0xb7` render as `OP_NOP4`-`OP_NOP8`.
- Under a word, the splice operands and `OP_SPLIT` position follow bitcoin-sv v1.2.3 (`6504a3a`, `int_serialization.h:61-118`, `interpreter.cpp:1708-1721`); the default mode retains the TypeScript SDK's unrestricted number reader (0.3.33, bsv-rs#41).
- TS's `Beef.verifyValid` reads a BEEF carrying a raw transaction with no input as valid (`ts-stack@edf6e03` `Beef.ts:1054-1075`); this crate's `verify_valid` and streaming reader refuse it, following the node (0.4.1, bsv-stack-lean #58). The same for one with no output (`NoOutputs`, 0.4.3, bsv-stack-lean #59), `Transaction::verify` refuses both for every transaction it reaches, proven or not; TS's `Transaction.verify` refuses them for an unmined transaction only, inputs first (`ts-stack@edf6e03` `Transaction.ts:1336-1342`, called at `:1654`), and never asks of a proven one.
- The whole-BEEF path follows the streaming reader where the reference does not (0.4.2, bsv-stack-lean #61): `Beef::from_binary` refuses a byte after the frame (TS's `fromBinary` is a prefix parser, its `fromBinaryStrict` refuses; `Beef.ts:1286-1309`); `verify_valid` refuses a lone leaf at an offset other than 0 (TS's `MerklePath` returns the txid at any offset, `MerklePath.ts:345,390-391`; this crate's `MerklePath` now refuses it during parse and `compute_root` too, with the missing sibling's level and offset); `allow_txid_only` decides nothing, a txid-only entry being valid when a BUMP of the BEEF proves it (TS's flag accepts or refuses every entry, `Beef.ts:1101-1104`); the atomic rule is the reader's (until 0.8.0 positional: the subject last, every other entry spent later), where TS asks that every transaction be in the subject's ancestry (`Beef.ts:482-491`).
- The atomic rule on the subject's graph (0.8.1, BRC-95; `beef_stream::atomic_unreached`, one walk for both readers, the Lean's `finish`): the subject a raw transaction of the BEEF, every other entry reached from it through the inputs of every raw entry, proven or not (the owner's ruling, 2026-10-22), position not judged; the stream names the earliest unreached entry by the trie order, at its offset. TS ≥ 3 (`ts-stack@4d0ea63`, `@bsv/sdk` 3.0.0; npm 3.2.1) cuts the subject's graph at each proven transaction (`Beef.ts:420-434`, `#collectAtomicTransactions` stops at `#hasMatchingBump`; `isAtomic` `:482-491`, `verifyValid` `:1064`, `Transaction.ts:311` "Atomic BEEF contains unrelated transaction data"), as BRC-95's "up to the point where each input can be confirmed with a Merkle proof" reads: it refuses a raw ancestor behind a proof (the staged vectors `raw-unproven-ancestor-after-proven-descendant` and `subject-present-not-last`, `parity_class` `intended`), which this crate's readers accept, as they accept everything TS 3 and Go write, and what TS 2.1.4 writes save an entry outside the graph (its `toBinaryAtomic` does not trim one: the vector `unrelated-transaction`, refused by every reader but 2.1.4's). Until 0.8.0 the rule was positional and refused the TS 2 writer's order, a raw unproven ancestor after its proven descendant (the bsv-dd x402 refund, P0-65). `@bsv/sdk` 2.1.4's reader does not judge the graph (`Transaction.fromAtomicBEEF`, `Beef.verifyValid` accept an unrelated entry); its `toBinaryAtomic` cuts every entry the sort puts after the subject (`getBeefForAtomic`), and its `BeefTx` names an entry built from raw bytes by the unreversed hash (`BeefTx.ts:51-53`: `mergeRawTx` of a proven transaction gives it a byte-reversed txid). Go's reader asks only that the subject be present (`NewBeefFromAtomicBytes`); its `AtomicBytes` cuts the ancestry at each proof.
- A transport fault is typed (Unreleased, bsv-rs#87): a broadcaster's send failure is `NEVER_SENT` or `MAY_HAVE_BEEN_RECEIVED`, a 429 (or a 503 with `Retry-After`) `RATE_LIMITED` with its wait, a 502, 503 or 504 `MAY_HAVE_BEEN_RECEIVED`, the status read before the body; TS's ARC answers `'500'` for a thrown fetch and the status as a string for a non-2xx (`ts-sdk@9e3ede6` `ARC.ts:189-195,219-222`), Go's `"500"` for a send or body-decode error (the body decoded before the status, `go-sdk@2ca481c` `transaction/broadcaster/arc.go:162-180,245-249`); neither reads `Retry-After`. The stack's rule (matrix rows 26 and 30) is the reason.
- The French, Japanese, Korean and Spanish BIP-39 wordlists are stored in Unicode NFC (as the crate's arrays always were); upstream `bitcoin/bips@100ba872` and `go-sdk@2ca481c` ship them in NFD, and BIP-39 asks NFKD of a wordlist (`bip-0039.mediawiki:86-87`). `Mnemonic::word_index` compares bytes, so an NFD phrase from Go or a Trezor-style wallet is refused as `InvalidMnemonicWord` where Go accepts it; TS ships English only. The fix normalizes both sides of the lookup and changes what a phrase is: the owner's word, the follow-up issue filed with #89.
- One reader for both paths (Unreleased, bsv-rs#86): `Beef::from_binary` is the streaming reader's decoder in a collect mode, so the whole path refuses what the stream refuses where TS reads otherwise (`ts-stack@4d0ea63`): a V2 format byte other than 0, 1, 2 (TS reads it as a raw transaction, `BeefTx.ts:293-301`), a V1 has-BUMP byte other than 0, 1 (TS reads any nonzero byte as "a BUMP index follows" and the index from the next varint, `:306` at `edf6e03` and `4d0ea63`), a leaf flag other than `00`, `01`, `02` (TS reads its bits, `MerklePath.ts:133-140`), the node's transaction rules in `verify_structure` (TS's `verifyValid` has none); a repeated leaf offset is refused on both paths as TS refuses it (`MerklePath.ts:221`), `DuplicateOffset` at the second leaf, where Go keeps the later leaf (`go-sdk@2ca481c` `transaction/merklepath.go:87-90`).
