# fix-697: the HTTP wallet's typed reading measured apart from the transport

Base `origin/beta` at `7896671d`. Issue #697: the array-form memory pin
(`test_http_json_success_tx_in_the_array_form_costs_the_typed_reading`, added by
`e0015348` for #339) failed on PR #691's run (11:13Z, 2026-11-03) and on PR #694's
re-run (11:32Z) with the same figure, 2,218,461 B for 468,692 B of text (4.73 times
against the bound of 4), and passed on the same code otherwise.

## What the pin measured

The profiler bracketed `HttpWalletJson::create_action` against a wiremock server in
the same process, so the peak held the mock's copy of the body, the client's
accumulated bytes (`result_values::response_bytes`, a `Vec` grown chunk by chunk,
`src/wallet/substrates/result_values/boundary.rs:145-155`), #408's snapshot and the
typed result. How many of those are alive at once is the scheduling's choice.

## The reader measured

The substrate's reader of a 200 answer is `answer::success`
(`src/wallet/substrates/http_json/answer.rs:80-105`), `pub(super)` and taking a
`reqwest::Response`, so no integration test reaches it without a transport. Its
typed reading is `serde_json::from_slice::<R>(&text)` at `answer.rs:89`, `R` the
public `CreateActionResult` for createAction, whose `tx` is a plain
`Option<Vec<u8>>` (`src/wallet/types.rs:705-706`). The new pin runs that reading on
the body already in memory, the profiler started after the fixture is built.

Not in the window: #408's `result_values::validate` (crate-private), which runs
before the typed reading. The end-to-end figure still covers it.

then `from_value`. Both pins fail on it, the new one with no server in its window.

## The witness of the flake

- Under background QoS (`taskpolicy -c background`, the loop stopped after ten
  minutes with two runs done) the wiremock peak moved from 1,342,553 B to
  1,467,302 B: the figure depends on the scheduling.
- A scratch test serving the same body from a raw loopback listener
  (`127.0.0.1:0`) in pieces with a yield and a 1 ms sleep between them moved the
  peak from 2.98 to 3.81 times the text (whole body 3.20, 256 KiB 3.24, 64 KiB
  3.81, 16 KiB and below 2.98): how the body is chunked on arrival changes how
  many copies are alive at the peak.
- The 2,218,461 B state did not appear locally. Its excess over the quiet figure
  is 875,908 B (1.87 bodies), consistent with one more body's worth plus an
  accumulator reallocation, and not proven to be the mock's write buffer alone.

## The end-to-end figure's treatment

Kept, printed, and asserted under five times the text, with the comment naming
the reason (one more body's worth alive on a loaded runner, the 4.73-times state
quoted). It is kept as an assertion because it is the only pin on the
substrate's order (typed reading first, the `Value` fallback only on refusal),
which the new pin cannot see; a `Value` reading stays far past it (19.9 times).

## The cold read's reading of the excess (a reading, not a proof)

wiremock 0.6 clones the template's body into each response
(`response_template.rs:323`, `self.body.clone()`), after the profiler starts, so
the mock's copy is most likely already inside the quiet figure: 1,342,489 B is
about the mock's copy (468,692), the client's accumulator at its doubled
capacity (524,288), the typed reading (262,240) and #408's snapshot. The
loaded state's excess (875,908 B) then fits the client side better than a
second mock copy: hyper 1.x grows its read buffer adaptively up to
`DEFAULT_MAX_BUFFER_SIZE` (8,192 + 4,096 * 100 = 417,792 B, `proto/h1/io.rs:23`)
when the body is already waiting in the socket, which a client task scheduled
late on a loaded runner sees, and the accumulator
(`result_values/boundary.rs:145-155`, `Vec::new()` with no reserve from the
Content-Length) grows in a different pattern with larger chunks. The lane's
piece-size witness (2.98 to 3.81 times with the server's write unchanged)
points the same way. Neither reading is proven; the five-times bound holds
both.
