# #744: the by-type discovery keeps the asked type alone; the parsers' lock position pinned at the decode call

Base `cbf27827` (`origin/beta`'s tip at the lane's start). PR #742 (#739, the
subject filter at the two `discover_*` doors) was open, not landed: this
change sits on the tip without it. Its by-type pins ask the certificates'
real type after its fold, so the two filters compose when either lands over
the other; #742's `subject_of` helper in `tests/identity_lock_position_537.rs`
(and its `02aa` fallback) is not on this base, so the brief's item replacing

## Item 1: the type filter

`discover_certificates_by_type(identity_key, cert_type)` sent the type in the
`ls_identity` query and never checked it on what came back. It now keeps a
certificate only when `cert.type_base64() == cert_type`, after every output
is parsed (the `?` on a limit unchanged).

The comparison: the canonical base64 text, exactly. Every token the parsers
read carries a `type` of canonical base64 of 32 bytes or is skipped (#553,
`client_record.rs`, `Certificate.ts:233-238`), so `type_base64()` re-encodes
to the token's own text, and comparing texts is comparing bytes whenever the
asked text is canonical. An asked text no token can carry (unpadded, with
white space) matches nothing rather than being decoded leniently: the door's
caller passes the same text to the lookup service, and a text the service
and the record rules disagree on is no type either side can answer. The
reference has no by-type door (`DiscoverByIdentityKeyArgs` carries no type at
`ts-stack@edf6e03`), and no `certificateTypes` filter on the identity-key
path (`identityUtils.ts:247-255` filters by subject, `:283-302` by
attributes), so there was no reference comparison to copy.

The pin, `tests/identity_discover_type_744.rs`: #553's `reference` token
(#737's, type `AQEB...AQE=`) and the same record with its type set to
`[3; 32]`, re-signed by the certifier 7 (`Certificate::sign`) and revealed by
the subject 9 (getPublicKey and createSignature for anyone, `PushDrop::lock`),
both outputs proven by a block of their own on an injected `.invalid`
resolver.

## Item 2: the lock-position pin

The token check cannot pass on a lock-after token by construction:
`is_authenticated_token` (`client_token.rs`) refuses unless
`is_canonical_signed_pushdrop(script, fields)` holds, and that function
(`token_envelope.rs:24-34`) requires `chunks[0]` a 33-byte push and
`chunks[1]` `OP_CHECKSIG`, the lock-before layout. A lock-after token's
leading chunks are its two fields. So the brief's fallback applies: the pin
is at the decode call.

Both parsers now call one crate-private function, `decode_token`
(`PushDrop::decode_before(script).ok()`), so the decode site is one place.
`src/identity/client_decode_token_744_tests.rs` takes #553's `reference`
token, decodes it, relocks the same key and the same two fields (the same
signature over the same bytes) with `LockPosition::After`, and asserts:
`PushDrop::decode` reads it with the same key and fields; the token check
refuses it; `decode_token` refuses it.

The mutation, in the scratch copy overlaid with the tip's `src/` and
`tests/`, `decode_token`'s body changed to `PushDrop::decode(script).ok()`:

```

the parsers' decode site reads lock-before alone
```

Under the same mutation `tests/identity_lock_position_537.rs` passes 2 of 2,
as #742's cold read measured. Its relocked control is unchanged.
