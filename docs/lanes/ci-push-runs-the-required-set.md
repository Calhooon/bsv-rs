Branch `lane/ci-push-runs-the-required-set` from `origin/beta`'s tip. The owner's word at 20:1xZ, 2026-10-27 (through the keeper, verbatim on the stack's rulings page): "sick of seeing all these CI failures... why are none of them passing... they are all so hardcore and slowing us down". The keeper's read: beta's last push run was red on the Benchmark Regression Check alone, a job that judges the runner's load, not the commit. Nothing is lost: the measurements still run before every tag. A job that only runs on a pull request today (`semver`, `beta-born`, `main-in-beta`'s condition) keeps its condition; the required set on a push is the subset that makes sense on a push (a push has no base ref: say which required jobs cannot run on a push and leave them to the pull request, as `semver` is). `dependents` is required on `main`: it stays on pull requests to `main` and on pushes to `main`, and leaves pushes to `beta` (today `dependents-plan`, `dependent-check` and `dependents` run on every push: `if: github.event_name != 'pull_request' || github.base_ref == 'main'`). The `wasm32 (combined)` context comes from a matrix job whose key carries digits; keep its name and its pull-request run exactly.

## What to do

1. `ci.yml`: on `push` to `main` or `beta`, only the line's required set runs (the same jobs a pull request to that line runs, minus those that need a pull request); every other job leaves the push run: `docs`, `actionlint`, `msrv`, `features`, `machete` (unused dependencies), `benchmarks-build`, `benchmarks` (Benchmark Regression Check), `scoreboard`, and on `beta` the dependents jobs. Each leaving job class goes into its own workflow under `.github/workflows/` with `workflow_dispatch` and `workflow_call` (so `release.yml` runs it before a tag), its own name and its own badge in README: the benchmark regression check and the scoreboard in `bench.yml` (the scoreboard needs the bench artifact; keep the `bench_baseline_record` input there), `msrv.yml`, `features.yml` (every feature builds alone and the wasm32 slices that are not the required `wasm32 (combined)`), `machete.yml`, `docs.yml` (rustdoc and actionlint together as "the checks of the text"). The `workflow_call` secrets (`DEPENDENTS_READ_TOKEN`, `BSV_SCRIPT_CORPUS_TOKEN`) move with the jobs that read them. The concurrency group of `ci.yml` stays; say in the entry that a cancelled run under it is never a red (and make the README badge query the required-set workflow on `main` with `?branch=main`, so a cancelled or in-progress beta push never shows as red there).
2. `release.yml`: before publishing a tag it already calls `ci.yml`; it now also calls each measurement workflow (`bench.yml`, `msrv.yml`, `features.yml`, `machete.yml`, `docs.yml`, and `nightly.yml`'s oracles if it is callable: read it; if not, say so and RELEASING.md names the dispatch as a step before the tag), so "once before a tag" holds for every job that left the push run; a prerelease tag runs them too (the beta.2 bump is tonight).
3. `nightly.yml`: unchanged if it is already dispatch-only (#351); read it and say.
4. The docs: `CLAUDE.md`'s layout row, `docs/NIGHTLY.md`, `docs/ARCHITECTURE.md`, `benches/README.md`, `docs/RATCHETS.md`'s baseline rules, `RELEASING.md` (the pre-tag measurements as a step in the ritual, points 1 to 10 and 14), `README.md` (the CI paragraph and the badges: one per workflow, the required-set badge first), `HANDOFF.md`'s "The lines" bullets (the push runs the required set). The proof: `actionlint` green on every workflow; `python3 -c 'import yaml'` parses each (or `yq`); a dry reading of each job's `if:` for `push` to `beta`, `push` to `main`, `pull_request` to each and `workflow_dispatch`, written in the REPORT as a table of job by event; the required contexts' names grepped unchanged.
