**The work.**
1. **The guard on beta.** A job `main-in-beta` in `ci.yml` running on every PR into beta and every push to beta: with `fetch-depth: 0`, it fails if `origin/main` is not an ancestor of the PR's merge base or beta's tip (`git merge-base --is-ancestor origin/main HEAD`), printing the commits main has that beta lacks (`git log --oneline HEAD..origin/main`) and the one sentence of what to do (merge main into beta through a PR; the sync workflow opens it). Required on beta: say so in the report; the captain flips the protection.
2. **The sync workflow.** `.github/workflows/sync-main-into-beta.yml`: on every push to `main`, it opens (or updates) a PR from a branch `sync/main-into-beta` (a merge of main into beta, `--no-ff`, never a rebase: main's commits keep their shas so the ancestor check holds) into `beta`, titled `sync: main into beta at <sha>`, with the list of commits in the body; if the merge conflicts, the PR is opened with a conflict marker list in the body and a label `needs-hand`; idempotent on a rerun (one open PR at a time, updated in place). Uses the `GITHUB_TOKEN` with `contents: write, pull-requests: write`; `persist-credentials: false` on the checkout as the other workflows do, with an explicit token on the push; `actionlint` clean; `gh` or the REST API for the PR, no third-party action (the house pins actions by sha: match). This file lands on beta and on main by a cherry-pick PR the captain opens (a workflow on `push: main` must live on main to fire).
3. **The direction rule, written down.** `RELEASING.md` gains the four classes main accepts and the sentence "every main commit is a cherry-pick of a beta commit with its test; `main-in-beta` fails until main's commits are merged back"; `docs/lanes/README.md` gets one line. `CHANGELOG.md`: a `### Changed` line under `[Unreleased]` for the two jobs (CI only).
