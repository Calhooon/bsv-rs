# #683: the nightly's weekly bench under the same edge as `ci-full`

The keeper's fleet line (2026-11-03): no two heavy jobs of this crate hold the
account's twenty hosted runners at once. #682 capped the shards and the fuzz
targets and sequenced `ci-full` after them; #692 brought the cap to 6. One
site stayed outside: the nightly's weekly `bench` job.

## The job's kind

`bench` is a dispatch job: one runner that runs `gh workflow run bench.yml`
on the line. The run it starts is a whole `bench.yml` run: `Benchmarks Build`
(`ubuntu-latest`) and `Benchmark Regression Check` (`ubuntu-24.04`) at once,
then `scoreboard` after both. No matrix, so no `max-parallel` applies; the
run's width is two jobs, its length about 19 minutes by the three release-called runs of 2026-10-30 (17m56s, 18m31s and 18m24s for the regression check, the build about 3 minutes, the scoreboard seconds), far inside the 55-minute give-up; a dispatched run of its own is unwitnessed until the Sunday on a branch dispatch (no
`bench.yml` dispatch run exists at `ba0952c9`; release run 41324499622's call
ran the build in 3m08s and the scoreboard in 5 s, the regression check
skipped on a tag).

## Before (`ba0952c9`)

```yaml
  bench:
    name: Bench (weekly)
    if: ${{ inputs.weekly }}
    runs-on: ubuntu-latest
    timeout-minutes: 5
    permissions:
      actions: write
    steps:
      - name: Dispatch bench.yml on the line
        env:
          GH_TOKEN: ${{ github.token }}
          LINE: ${{ github.ref_name }}
        run: gh workflow run bench.yml --repo "$GITHUB_REPOSITORY" --ref "$LINE"
```

No `needs`: on a Sunday night (`-f weekly=true`) the job ran at the start of
the run, beside `source`, and its dispatched run asked for its two jobs
beside the opening wave of six shards. The guard read a heavy matrix or a
dispatch of `ci.yml` as heavy, so it did not see the bench.

## After

```yaml
  bench:
    name: Bench (weekly)
    needs: [mutants, fuzz, ci-full-beta]
    if: ${{ !cancelled() && inputs.weekly }}
    runs-on: ubuntu-latest
    timeout-minutes: 60
    ...
      # list the bot's bench.yml dispatch runs on the line, dispatch,
      # take the new one, `gh run watch` under a 55-minute give-up,
      # read its conclusion, `failure` fails the job; set -euo pipefail

  ci-full-main:
    needs: [ci-full-beta, bench]
    if: ${{ !cancelled() }}
```

The order on a Sunday night: the shards (6 at a time), the fuzz targets (6),
beta's `ci.yml` run (up to 9, plus the waiting job), the bench's run (2, plus
the waiting job), main's `ci.yml` run (up to 22). On another night `bench` is
skipped and `!cancelled()` lets `ci-full-main` follow beta's run as before.

Why between beta's and main's, not after main's: `ci-full-main` dispatches
and ends without waiting, so a bench after it would start beside main's 22.
Why not beside beta's (`needs: [mutants, fuzz]` alone): beta's 9 and the
bench's 2 with the two waiting jobs make 13, two heavy runs at once, which
the line refuses. The cost: on a Sunday main's dispatch waits for the
bench's run (its length on a branch dispatch is the next Sunday's
measurement), and the bench job holds one runner while it waits.

## The guard

- `is_heavy_job`: a heavy matrix, or a job with a non-comment
  `gh workflow run <file>` line (any workflow, by the rule, not a list);
  `edge_errors` refuses every pair of such jobs with no `needs:` path.
- `HEAVY_EDGES` gains four: `bench` needs `mutants`, `fuzz`, `ci-full-beta`;
  `ci-full-main` needs `bench`.
