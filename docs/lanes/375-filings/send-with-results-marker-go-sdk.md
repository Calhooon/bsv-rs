# createAction and signAction results: an absent sendWithResults panics on the wire's absent marker, and a nil one is written as a zero count instead of the marker

Repository: bsv-blockchain/go-sdk

Prepared for filing by Calhooon (owner). Draft only; no issue was created. Census pointer: bsv-rs#375. No census row records this field. CHANGELOG.md names `sendWithResults` in #473's bound tables (lines 3097, 3151-3154, 3194-3197: the 1001 cap and the remaining-bytes check, which this crate shares with the reference) and its parity note (line 3242: Go's `create_action_result.go:70-108` read without these caps), in #487's and #432's result-validation rows (lines 2578, 3315, 3328) and in #339's code-5 rows (lines 8656-8678, 8766); none records the absent marker. Census row 10 (The wallet wire's client-side bounds (#473) are the reference's (WalletWireTransceiver.ts…) is the nearest row, but it records bounds. This is the reference's own wire broken between its SDKs, not a choice of the port.

BRC-100 frames `sendWithResults` in the createAction and signAction results as a VarInt count followed by the entries, or `VarInt -1` (nine `ff`) when absent. TypeScript writes and reads exactly that. go-sdk's `readTxidSliceWithStatus` reads the count with `ReadVarInt` and calls `make([]wallet.SendWithResult, 0, count)` with no check. On the absent marker the count is 2^64-1, and the reader panics with `runtime error: makeslice: cap out of range` (`status.go:54`) instead of returning an error. A TypeScript wallet writes that marker on every createAction or signAction result that carries no `sendWithResults`, for example the `{ txid }` results of the steps below. So a Go client that reads such a result dies on valid input. go-sdk's writer, `writeTxidSliceWithStatus`, writes a nil list as `00`, a count of zero, where the wire's absent marker is nine `ff`, so a TypeScript client reads go-sdk's absent list as an empty one.

Steps to reproduce (go-sdk at 2ca481c and at 9f4c4a658, the same output; ts-stack at edf6e03 under Node 22.18.0). The txid is `31×32` (32 bytes of `0x31`). The results are `{ txid }` for both calls, with createAction args `{ description: 'fixture action', options: { returnTXIDOnly: true } }` and signAction args `{ spends: {}, reference: 'AAAA', options: { returnTXIDOnly: true } }`.

1. TypeScript writes, go-sdk reads.
   - The TypeScript wallet's createAction result frame (the reference's processor over a stub wallet): `00` `01` `31×32` `00` `ffffffffffffffffff` **`ffffffffffffffffff`** `00`. In order: the frame's error byte, the txid flag and txid, the tx flag, `noSendChange` absent, **`sendWithResults` absent**, no signable transaction.
   - The TypeScript wallet's signAction result frame: `00` `01` `31×32` `00` **`ffffffffffffffffff`**.
   - `serializer.DeserializeCreateActionResult` on the createAction frame panics:
     ```
     panic: runtime error: makeslice: cap out of range
     github.com/bsv-blockchain/go-sdk/wallet/serializer.readTxidSliceWithStatus(...)
         wallet/serializer/status.go:54
     github.com/bsv-blockchain/go-sdk/wallet/serializer.DeserializeCreateActionResult(...)
         wallet/serializer/create_action_result.go:79
     ```
   - `substrates.WalletWireTransceiver.SignAction`, over a `WalletWire` that answers the signAction frame, panics with the same `runtime error: makeslice: cap out of range`, and so does `serializer.DeserializeSignActionResult` on the frame without its error byte. That is go-sdk's own client path: `transmit` strips the error byte with `ReadResultFrame`, then `DeserializeSignActionResult` calls `readTxidSliceWithStatus`.
   - A present list does not panic: with `sendWithResults: []` the reference writes `00` there, and with one `sending` entry it writes `01` `31×32` `02`. `DeserializeCreateActionResult` returns `nil` for the first (`if count == 0 { return nil, nil }`, `status.go:50-51`: the reference's present, empty list read as absent, the writer's conflation in reverse) and `[{31…31 sending}]` for the second; `DeserializeSignActionResult` returns `nil` for `00` too.
2. go-sdk writes, TypeScript reads.
   - `serializer.SerializeCreateActionResult` for `{ Txid }` (nil `SendWithResults`): `00` `01` `31×32` `00` `ffffffffffffffffff` **`00`** `00`. `serializer.SerializeSignActionResult` for `{ Txid }`: `01` `31×32` `00` **`00`**, framed by `WriteResultFrame` as `00` `01` `31×32` `00` **`00`**. The writer gives a nil `sendWithResults` the zero count, where the absent `noSendChange` beside it gets the nine `ff` marker.
   - The reference's client reads go-sdk's signAction frame as `{"txid":"31…31","sendWithResults":[]}`. It reads the createAction bytes above the same way when they are handed to it as the frame. It does not refuse them: an absent list comes back as an empty one, and the TypeScript caller cannot tell "no sendWith batch" from "a batch with no results". On the reference's own absent marker, the same client returns `{"txid":"31…31"}` with no `sendWithResults` member.

Expected: the field read and written as BRC-100 and the reference frame it. A count of 2^64-1 (nine `ff`) reads as absent (`nil`), a count of `0` as a present, empty list, and a nil list is written as nine `ff`, in `readTxidSliceWithStatus` and `writeTxidSliceWithStatus`, for createAction and signAction alike. The list is never sized from the marker's bytes. A count is bounded by the bytes that remain (33 per entry) before anything is allocated, so no count can panic. bsv-rs follows the reference: its reader returns `None` for the nine `ff` and bounds any other count by the remaining bytes and by 1001 before allocating, and its writer writes nine `ff` for `None` and the count otherwise.

Actual: at both shas, `readTxidSliceWithStatus` reads the count with `ReadVarInt` and returns `nil` only for `0`, so a present, empty list reads as absent. Any other count, the marker included, reaches `make(..., 0, count)`. `writeTxidSliceWithStatus` writes `WriteVarInt(0)` for nil. The three serializer files are byte-identical between 2ca481c and 9f4c4a658 (`git diff 2ca481c 9f4c4a658` is empty for `status.go`, `create_action_result.go` and `sign_action_result.go`, and `Reader.ReadVarInt` is unchanged at `util/reader.go:76`).

Noted, and not this issue's ask: go-sdk's `SerializeCreateActionResult` writes its own success byte (`create_action_result.go:15-16`) inside the result frame's error byte (`WriteResultFrame`, `frame.go`), and `DeserializeCreateActionResult` expects it (`:58-61`). So a frame that a TypeScript wallet writes reaches `WalletWireTransceiver.CreateAction` without that inner byte and is refused first, `response indicates failure: 1`, before `sendWithResults` is read. signAction's result has no inner byte, which is why the panic reaches go-sdk's own client through `SignAction`.
