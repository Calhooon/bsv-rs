# createAction's noSendChange is framed behind an extra byte length, so a Go wallet and a TypeScript client cannot read each other's list

Repository: bsv-blockchain/go-sdk

Prepared for filing by Calhooon (owner). Draft only; no issue was created. Census pointer: bsv-rs#375. Census row 10 (The wallet wire's client-side bounds (#473) are the reference's (WalletWireTransceiver.ts…) is the nearest row, but it records the count's bounds, not this framing, and no census row states the framing: this is the reference's own wire broken between its SDKs, not a choice of the port.

BRC-100 frames createAction's `noSendChange`, in the options and in the result, as a VarInt count followed by the outpoints, `VarInt -1` when absent. TypeScript writes and reads exactly that. go-sdk writes the count and the outpoints into a byte string and then writes that string with `WriteOptionalBytes`, so a byte length comes before the count; its readers take `ReadOptionalBytes` and then `decodeOutpoints`. The absent list (nine `ff`) reads the same on both sides; a present list does not, on either path. A Go wallet serving a TypeScript client, or a TypeScript wallet serving a Go client, refuses the other's createAction the first time `noSendChange` carries an outpoint.

Steps to reproduce (go-sdk at 9f4c4a658 and at 2ca481c, the same output; ts-stack at edf6e03 under Node 22.18.0). The outpoint is `3131…31.2` (32 bytes of `0x31`, index 2); the args are `{ description: 'fixture action', options: { returnTXIDOnly: true, noSend: true, noSendChange: [outpoint] } }`, the result `{ txid: 3131…31, noSendChange: [outpoint] }`.

1. TypeScript writes, go-sdk reads.
   - The TypeScript client's request params (after the call byte `01` and the empty originator `00`): `0e6669787475726520616374696f6e` `ff…ff` (six absent fields, nine `ff` each) `01` `ffffff` `ffffffffffffffffff` `01` `01` **`01` `31×32` `02`** `ffffffffffffffffff` `ff`.
   - The TypeScript wallet's result (the reference's processor over a stub wallet): `00` `01` `31×32` `00` **`01` `31×32` `02`** `ffffffffffffffffff` `00`.
   - `serializer.DeserializeCreateActionArgs` on the params: `error deserializing options: error decoding noSendChange: error reading bytes reverse: read past end of data`. `serializer.DeserializeCreateActionResult` on the result: `error decoding noSendChange: error reading bytes reverse: read past end of data`. go-sdk reads the count `01` as a byte length, takes the first txid byte `31` as the body, reads it as a count of 49 and runs off the end of that one-byte body. (Read from the code, not run: a txid whose first byte is `00` gives an empty list instead, and the outpoint's other 32 bytes are then read as `sendWith` and the fields after it.)
2. go-sdk writes, TypeScript reads.
   - `serializer.SerializeCreateActionArgs` for the same args: the same params except the field, **`22` `01` `31×32` `02`** (a byte length of 34, then the count).
   - `serializer.SerializeCreateActionResult` for the same result: `00` `01` `31×32` `00` **`22` `01` `31×32` `02`** `00` `00`.
   - The reference's processor on go-sdk's request answers the error frame `01` + `Invalid createAction noSendChange length: exceeds the remaining Wallet Wire frame`, and the wallet is never called. The reference's client on go-sdk's result throws `Wallet Wire createAction noSendChange count exceeds the remaining response data`. TypeScript reads the length `0x22` as a count of 34 outpoints, which the 36 bytes left cannot hold.
3. An empty list (read from the code, not run): go-sdk writes `01 00`, which TypeScript reads as one outpoint whose txid starts at `00`. TypeScript writes `00`, which go-sdk's `ReadOptionalBytes` reads as absent, so `[]` comes back as `nil`.

Expected: the field framed as BRC-100 and the reference frame it, a VarInt count then the outpoints, with no outer length, in `encodeOutpoints`' callers and in `decodeOutpoints`' callers, on the args and on the result. bsv-rs follows the reference's framing: its transceiver writes the count then the outpoints and reads them the same way, and its recorded frames carry the reference's bytes for the field.

Actual: go-sdk writes `WriteOptionalBytes(encodeOutpoints(...))` and reads `decodeOutpoints(ReadOptionalBytes())` at both shas, with the same lines. The only change between the shas in these files is the outpoint index read (`ReadVarInt32`, PR #392), which does not touch the framing.
