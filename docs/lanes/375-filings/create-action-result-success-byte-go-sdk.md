# createAction's result carries an extra success byte inside the frame that the wire does not define, so a Go client refuses every TypeScript result that carries a txid and a TypeScript client misreads Go's

Repository: bsv-blockchain/go-sdk

Prepared for filing by Calhooon (owner). Draft only; no issue was created. Census pointer: bsv-rs#375. No census row records this byte: CLAUDE.md's divergence list and `docs/census/legs-2026-10-31.{md,json}` do not name it, and CHANGELOG.md names `create_action_result.go` only in #487's parity note (line 2772: the deserializer's line range, about result validation) and #473's (line 3339: the collection caps). Row 21's draft notes the byte as "not this issue's ask". This is the reference's own wire broken between its SDKs, not a choice of the port.

BRC-100 frames every wallet response as one error byte (`0` on success) followed by the method's return values; createAction's return values start with the txid flag. TypeScript writes and reads exactly that. go-sdk's `SerializeCreateActionResult` writes a second success byte of its own before the txid flag, and its processor then frames that output with `WriteResultFrame`, which writes the frame's error byte in front of it. So go-sdk's createAction response starts `00 00`. `DeserializeCreateActionResult` expects the inner byte, and go-sdk's client hands it the bytes after `ReadResultFrame` has already taken the frame's error byte. go-sdk talks to itself correctly. Against TypeScript, each side reads the other's first result byte as a different field. No other result serializer does this: signAction's result, for example, starts with the txid flag (`sign_action_result.go:13-15`).

Steps to reproduce (go-sdk at 2ca481c and at 9f4c4a658, the same output; ts-stack at edf6e03 under Node 22.18.0). The txid is `31×32` (32 bytes of `0x31`). The args are `{ description: 'fixture action', options: { returnTXIDOnly: true } }` and the result is `{ txid }`.

1. TypeScript writes, go-sdk reads.
   - The TypeScript wallet's createAction response (the reference's processor over a stub wallet): `00` `01` `31×32` `00` `ffffffffffffffffff` `ffffffffffffffffff` `00`. In order: the frame's error byte, the txid flag and txid, the tx flag, `noSendChange` absent, `sendWithResults` absent, no signable transaction.
   - go-sdk's own client, `substrates.WalletWireTransceiver.CreateAction`, over a `WalletWire` that answers those bytes, returns `response indicates failure: 1`. `transmit` takes the frame's `00` with `ReadResultFrame`, and `DeserializeCreateActionResult` reads the txid flag `01` as its success byte (`create_action_result.go:59-60`).
   - The same response with `sendWithResults: []`, `00` `01` `31×32` `00` `ffffffffffffffffff` `00` `00`, which has no absent marker for row 21's reader to panic on, is refused the same way, `response indicates failure: 1`.
   - `serializer.DeserializeCreateActionResult` on either response with its frame byte removed (the bytes go-sdk's client passes it) returns the same `response indicates failure: 1`. Handed the whole response, frame byte included, the deserializer reads the frame byte as its success byte and reads the rest. That is how rows 20 and 21 reached the fields after it.
   - go-sdk's own test pins the byte: `TestDeserializeCreateActionResultErrors`, case "invalid txid length" (`create_action_result_test.go:92-101`), writes a result that starts with the txid flag `1` and expects `response indicates failure: 1`.
   - A TypeScript result without a txid (read from the code, not run): its txid flag `00` passes as go-sdk's success byte, so every later field is read one byte early, starting with the tx flag read as the txid flag.
2. go-sdk writes, TypeScript reads.
   - `serializer.SerializeCreateActionResult` for `{ Txid }`: `00` `01` `31×32` `00` `ffffffffffffffffff` `00` `00`. go-sdk's processor, `substrates.WalletWireProcessor.TransmitToWallet`, over a stub wallet that answers `{ Txid }` for the args above, frames it as **`00` `00`** `01` `31×32` `00` `ffffffffffffffffff` `00` `00`. go-sdk's own client reads that back as the result.
   - The reference's client on go-sdk's response throws `ReaderUint8Array read exceeds available data`. It takes the frame's `00` (`WalletWireTransceiver.ts:136-139`), reads go-sdk's inner `00` as the txid flag, so no txid (`:238-240`), and reads `01` as the tx flag (`:242`). It then reads the first txid byte `0x31` as a tx length of 49 (`:243`), with 43 bytes left (`ReaderUint8Array.ts:38-48,67-68`). For a txid whose first byte is no larger than the bytes left, the reference reads that many bytes as `tx` and goes on from inside the txid (read from the code, not run).

Expected: createAction's result as BRC-100 and the reference frame it. The frame's one error byte is written by `WriteResultFrame` and read by `ReadResultFrame`, and the result starts with the txid flag, as go-sdk's signAction result already does: no success byte inside the frame, so `SerializeCreateActionResult` writes the txid flag first and `DeserializeCreateActionResult` reads it first. bsv-rs follows the reference: its client takes the frame's error byte once for every call and then reads createAction's txid flag first. Its recorded createAction responses, from the unmodified reference, have no byte between the two.

Actual: at both shas, `SerializeCreateActionResult` writes `WriteByteValue(0)` before the txid (`create_action_result.go:15-16`), `DeserializeCreateActionResult` refuses any first byte other than `0` (`:58-61`), and the processor and client add and take the frame's error byte around them (`frame.go:70-98,100-142`; `wallet_wire_processor.go:24-98,112-122`; `wallet_wire_transceiver.go:23-36,38-50`). `git diff 2ca481c 9f4c4a658` is empty for `create_action_result.go`, `create_action_result_test.go`, `sign_action_result.go`, `frame.go` and `wallet/substrates/`.
