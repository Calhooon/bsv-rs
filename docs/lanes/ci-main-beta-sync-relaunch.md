### (1) The design question
Facts read, not told:
- Both `beta` and `main` protection: `required_linear_history: true`, `enforce_admins: true`, the same five contexts required on beta (`Test Suite (ubuntu-latest, stable)`, `Clippy`, `Rustfmt`, `vectors`, `deny`).
- Main has four commits beta lacks by sha. Every one carries a `(cherry picked from commit <sha>)` trailer, and every named source is on beta:
```

82706c9 -> bdc0642 : on beta
218c82d -> e02d8ef : on beta
c76835c -> 3f0f6ef : on beta
```
- `git cherry origin/beta origin/main`: two `-` (patch-equivalent), two `+` (`c76835c`, `82706c9`: hand-resolved picks whose patch differs). Patch-equivalence alone misses half of today's commits; the trailer catches all four.
- The lane's merge design against the real lines today: `git merge --no-ff origin/main` from beta conflicts (`.gitleaks.toml` add/add, `CHANGELOG.md` content), so the opening sync PR is `needs-hand`.
Judgment. The lane's guard (sha ancestry) plus a `--no-ff` merge PR cannot land on beta: linear history refuses a merge commit, and a rebase or squash merge re-authors main's shas, so the guard stays red after the PR lands. Once required, every PR into beta is held forever. Step 19 of the lane's own RELEASING.md admits this and defers to a protection change. That change breaks step 12 ("protected as main is") and would be the only reason to give up linear history on beta. The merge design also does not enforce the second invariant: a commit born on main is merged into beta by the sync, and the guard is satisfied without the patch ever having been born on beta.
The link design holds both invariants with no protection change: a main commit is "on beta" when it is on HEAD by sha, by patch-id (`git cherry`), or by a cherry-pick link in either direction (main's commit names a beta source that is on HEAD, or a HEAD commit names it). I ran this guard against the real refs: green on `origin/beta` (1be93d8), red on `efe12e6` naming all four. It is required-able today. What it loses: a hand-resolved pick made without `-x` has no link and fails (so step 17 must say `git cherry-pick -x`, and the remedy is adding the trailer); a forged trailer passes (a process guard, not a security one). The cherry-pick sync re-authors the sha (not a house rule) and GitHub's rebase merge re-authors it again, but the trailer lives in the message body and the patch-id in the diff, so both survive. A release commit is main-born by nature and conflicts on `Cargo.toml` and `CHANGELOG.md` under either design: `needs-hand` once per release, the same hand work as today's real conflict.
Recommendation: relaunch with the link guard and a cherry-pick sync for a rebase merge. The second invariant at main's door is the same shell with the roles swapped (`git cherry HEAD origin/beta` on PRs into main, with an allowance for the release commit); make it the relaunch's third job or a follow-up issue. The guard's exact shell (shellcheck clean, run as above):
```bash
#!/usr/bin/env bash
# main-in-beta: every commit main has is on HEAD by sha, by patch, or by a cherry-pick link.
set -euo pipefail
git fetch --no-tags origin main
base="$(git merge-base origin/main HEAD)"
missing=()
while read -r mark sha _; do
  [ "$mark" = "+" ] || continue                       # "-": a patch-equivalent commit is on HEAD
  src="$(git log -1 --format=%B "$sha" | sed -n 's/.*(cherry picked from commit \([0-9a-f]\{40\}\)).*/\1/p' | head -1)"
  if [ -n "$src" ] && git merge-base --is-ancestor "$src" HEAD; then continue; fi   # main's commit names its beta source
  if git log --format=%B "$base..HEAD" | grep -q "(cherry picked from commit ${sha})"; then continue; fi   # a beta commit names it
  missing+=("$sha")
done < <(git cherry HEAD origin/main)
if [ "${#missing[@]}" -eq 0 ]; then
  echo "every commit of origin/main $(git rev-parse --short origin/main) is on $(git rev-parse --short HEAD) by sha, patch or cherry-pick link"
  exit 0
fi
echo "The commits main has that this tree lacks (no patch-equivalent, no cherry-pick link):"
for sha in "${missing[@]}"; do git log -1 --oneline "$sha"; done
echo "::error::main has ${#missing[@]} commit(s) beta lacks; cherry-pick each onto beta with -x through a PR (sync-main-into-beta.yml opens it from sync/main-into-beta) before this lands"
exit 1
```
The sync under this design: the same filter yields the `+` list; if empty, done; else `git checkout -B sync/main-into-beta origin/beta` and `git cherry-pick -x` each in main's order; on a conflict, `cherry-pick --abort` that one, keep the picks that succeeded, name the conflicting commit and files in the body, label `needs-hand`; push; the PR says "land by rebase merge". The rerun rule: leave the branch when it holds beta's tip and every `+` commit is linked from it.
### (2) The sync workflow's mechanics as written
- **M1, a defect.** `gh label create needs-hand` needs `issues: write`; the job grants `contents`, `pull-requests`, `actions` only, and the label does not exist in the repo (the label list has no `needs-hand`). Today's real merge conflicts, so the first live run dies at that step with the PR already open and unlabelled. Add `issues: write`, or have the captain create the label once and drop the create.
- **M2.** The rerun rule cannot wrongly skip: `current` needs both main and beta as ancestors of the branch, so any movement of main rebuilds. It can wrongly discard: a hand-resolved branch that has not landed when main moves again is rebuilt from beta and force-pushed to main's tip (dry run 6 below). The relaunch should merge or pick the new main commits onto the existing branch when it already holds beta's tip.
- **M3.** In the conflict state the branch is main's tip, so the dispatched `main-in-beta` passes trivially (main is its own ancestor) and the five required contexts go green on a PR GitHub cannot merge. Harmless, but the check misstates. The cherry-pick sync has no "main's tip" fallback state.
- `workflow_dispatch` on `ci.yml`: the five required contexts are not event-gated and run; `semver` and `benchmarks` skip; `ratchet` falls back to `--check` without `--against` when the PR base sha is empty (read at the job's step). GitHub attaches check runs to the commit sha and branch protection reads the latest run by context name on the PR's head sha, so a dispatched run satisfies the required checks; `strict: true` is met because the branch holds beta's tip. Neither the lane nor I ran a dispatch; the premise that a `GITHUB_TOKEN` push or PR starts no workflow is GitHub's documented rule.
- Token and permissions: top-level `contents: read`, job-level writes, `persist-credentials: false`, the push with an explicit `x-access-token` URL: correct. `actions/checkout` pinned at the same v4.4.0 sha as the other workflows. `actionlint` 1.7.12 clean on all five workflows.
