# #746: `query` keeps only what its question asked for; the revocation's lock position pinned at the decode call

Base `8a2cc173` (`origin/beta`'s tip at the lane's start, #745 landed: the
by-type filter and the parsers' decode-site pin this lane builds on).

## Item 1: `query`'s filters

`IdentityClient::query(IdentityQuery)` sent `identityKey`, `certificateType`
and `certifiers` to `ls_identity` and pushed every certificate the parser
admitted. It now keeps, after the walk, only the results whose certificates
match every field the question carries (`is_asked_certificate` in
`client.rs`, beside `is_asked_subject` and `decode_token`):

| Field | Its type | The comparison | Absent |
|---|---|---|---|
| `identity_key` | `Option<String>` | `is_asked_subject`: the subject's compressed hex against the asked text lower-cased (#737, #739) | no filter |
| `certificate_type` | `Option<String>` | `type_base64()` equal to the asked text exactly; a token's type is canonical base64 of 32 bytes (#553), so the text comparison is the bytes' (#744) | no filter |
| `certifier` | `Option<String>`, one key (the lookup sends it as a one-entry `certifiers` list) | the certificate's certifier key, compressed hex (lower case), against the asked text lower-cased | no filter |

The certifier field is not a list, so there is no empty list to read: unset
is no filter. Unset, the lookup body still asks the default SocialCert
certifier (`DEFAULT_SOCIALCERT_CERTIFIER`), as before; the answer is not
filtered by that default, because the question the caller wrote carries no
certifier and a filter on it would drop every certificate of every other
certifier the host returns (the #737 harness's certifier 7 among them).
`Some("")` is a certifier no key matches: it drops everything, as the
overlay given `[""]` would answer nothing. `attributes` is sent and not
checked on the answer (the parser has no attribute view of a certificate at
this door; out of the issue's three).

The walk and the error path unchanged: every output parsed in order, a skipped
one passed over, a `limit` anywhere the call's `IdentityError`.

The door has no reference counterpart (`IdentityClient.ts` at
`ts-stack@edf6e03` resolves through `resolveByIdentityKey` and
`resolveByAttributes`): hardening, the rule #739 and #744 set at the two
`discover_*` doors.

through `query(IdentityQuery::by_identity_key(key))`, depending on `query`
keeping every subject (the `other_subject_*` shapes count the other subject's
