# Lane fix-104: the duplicate dependency families re-measured on beta (#104)

A docs lane (`DRAFTED-DOCS`): the census, each family's constraint, and the
slices that would converge them. `Cargo.toml`, `deny.toml` and every workflow
are unchanged; no lockfile is committed. Part of #101 ("deny green with an
empty ignore list").

Measured 2026-11-09 at `c96f3c7e` (`origin/beta`'s tip, bsv-rs
0.9.0-beta.7), cargo 1.98.1, cargo-deny 0.20.2 installed under `$TMPDIR`.
The evidence (the lockfile, every tree, every inversion, the deny output,
the probes) is kept at `/Volumes/Lanes/out/bsv-rs/fix-104/census/`.

## The commands

In a scratch export (`git archive HEAD | tar -x -C "$TMPDIR/fix-104-census"`):

```sh
cargo generate-lockfile
shasum -a 256 Cargo.lock
cargo tree --locked --all-features --target all --duplicates -e normal,build,dev
cargo tree --locked --no-default-features --features "auth,wallet,transaction,overlay,socketio,wasm" \
  --target wasm32-unknown-unknown --duplicates -e normal,build,dev
cargo tree --locked --target all --duplicates -e normal,build,dev
cargo tree --locked --all-features --target all -e normal,build,dev -i <crate>@<version>   # each version
# the same -i on the wasm32 slice and the defaults for the pairs those graphs hold
cargo-deny --locked --all-features check
cargo-deny --locked --no-default-features --features "auth,wallet,transaction,overlay,socketio,wasm" \
  --target wasm32-unknown-unknown check
cargo-deny --locked check
```

The newest release of each parent was read from crates.io
(`/api/v1/crates/<crate>` for `max_stable_version`, then its
`dependencies`). The probes below each edit `Cargo.toml` in a throwaway
export, regenerate the lockfile and re-run the three `--duplicates` trees:
resolution only, nothing built.

## Since 0.8.2

The row's five families stand, syn now at 3.0.10. Six crates are new
duplicates, all from the k256 0.14 move (#125), which took the hashes and
the curves to the digest 0.11 generation while the symmetric ciphers, rand
and tungstenite stayed on the older one: `block-buffer`, `cpufeatures`,
`crypto-common`, `digest`, `rand_core`, `sha1`. In the row's terms the wasm32
slice held syn alone and now holds crypto-common and rand_core beside it;
the defaults held syn and windows-sys and now hold cpufeatures,
crypto-common and rand_core too.

### The probes (resolution only)

- **A**, `tokio-tungstenite = "0.30"`: all loses block-buffer, digest and sha1,
  gains rand (0.8.8, 0.10.3) and thiserror/thiserror-impl (1.0.69, 2.0.21);
  wasm32 and the defaults unchanged.
- **B**, `aes-gcm = { version = "0.11", default-features = false, features = ["aes", "alloc"] }`,
  `aes = "0.9"`, `cbc = "0.2"`: wasm32 down to rand_core and syn; the
  defaults down to rand_core, syn, windows-sys; all unchanged (tungstenite
  0.24 keeps digest 0.10, so crypto-common 0.1 and cpufeatures 0.2). With
  aes-gcm's default features (probe B0) getrandom 0.4 enters the wasm32
  slice and the defaults through `aes-gcm/getrandom`: the slice must turn
  them off.
- **A and B together**: all holds base64, core-foundation, getrandom,
  rand, rand_core, syn, thiserror, windows-sys (eight, from eleven); wasm32
  rand_core and syn; the defaults rand_core, syn, windows-sys.
- **thiserror 2**: no graph loses syn 2; all gains a thiserror pair.

## The follow-on slices (none made here)

- **(a) getrandom and rand, the owner's question.** Keep getrandom 0.2 and
  the duplicate, or move `rand` to 0.10 and `getrandom` to 0.4 with the
  `wasm` feature's `getrandom/js` replaced by `getrandom/wasm_js`
  (getrandom 0.4.3's feature), which every wasm32 downstream rebuilds
  (`docs/DEPENDENTS.md`). The census adds two facts: the getrandom pair
  sits in the all-feature graph alone, through tempfile under native-tls
  (native only, never in a Worker's build), and the rand_core pair, which
  does sit in the wasm32 slice, rides with the same rand 0.8. The drafter
  recommends keeping 0.2 for now; the lane agrees: the getrandom duplicate costs no
  wasm32 build anything.
- **(b) thiserror 1 to 2.** Not a lane: the probe shows no graph losing
  syn 2 (zerocopy-derive holds it in every graph). Revisit with (e), whose
  tungstenite 0.30 is on thiserror 2, or when zerocopy-derive moves. Any
  such move keeps every `Error` text byte for byte.
- **(c) memory-stats.** No release past 1.2.0; not a lane. A later lane
  could drop the dev-dependency if the tests it serves can count otherwise.
- **(d) base64 and core-foundation** wait on wiremock (base64 0.23) and
  hyper-util (system-configuration 0.8); the row stays open on them.
- **(e) the ciphers: aes-gcm 0.11, aes 0.9, cbc 0.2** (new since 0.8.2).
  Clears crypto-common from the wasm32 slice and the defaults and
  cpufeatures from the defaults (probe B). Constraints for that lane:
  aes-gcm without default features (else getrandom 0.4 enters wasm32);
  aes 0.9.3 and 0.9.4 declare rust-version 1.89 above the crate's 1.88
  (0.9.1 and 0.9.2 declare 1.85; 0.9.0 is yanked), and the edition 2021
  resolver is not MSRV-aware, so a fresh resolution takes 0.9.4 and the
  `msrv` workflow would read it: the lane bounds aes or raises the MSRV
  (the owner's word); the cipher 0.5 API move in
  `src/primitives/symmetric.rs` and `src/compat/ecies.rs` with every
  AES-GCM, AES-CBC and ECIES vector unchanged.
- **(f) tokio-tungstenite 0.24 to 0.30** (new since 0.8.2), the `websocket`
  feature (outside `full`, native only). Clears sha1, digest, block-buffer
  (probe A) and, with (e), crypto-common and cpufeatures from all; brings
  rand and thiserror pairs into all. tungstenite 0.26 onward changed the
  `Message` payload types (`Utf8Bytes`, `Bytes`), so
  `src/auth/transports/websocket_transport.rs` moves; MSRV 1.85.
