# #661: chunks built by hand with empty or misplaced data, against the reference

Base `c6781b4a` (`origin/beta`'s tip, 2026-11-03). The issue asked for a rule for a
`Script` built through the public `Script::from_chunks` with `ScriptChunk::new`
from chunks whose opcode and data disagree: refuse at construction, or have
`to_asm` write what the serializer writes. The reference decides, and it does
neither.

## The reference (`ts-stack@edf6e03`, `packages/sdk/src/script/`)

- `ScriptChunk.ts`: `{ op, data?, invalidLength? }`; `new Script(chunks)` holds
  any list, no check.
- Bytes: `#serializeChunksToBytes` (`Script.ts:474-490`) and `#writeChunkData`
  (`:539-562`): the opcode byte; the data bare after an opcode below
  `OP_PUSHDATA1` (`OP_0` included), with its length after a PUSHDATA opcode, not
  at all after any other opcode; after an `OP_RETURN` with data, the data and
  nothing more.
- ASM: `toASM` (`:222-229`) through `#_chunkToString` (`:668-677`): a chunk with
  data writes its data's hex alone, whatever its opcode; one without writes
  `OP[op]` (`OP_0` for `0x00`, the name listed before `OP_FALSE`, `OP.ts:6,223-226`;
  `undefined` for a direct push opcode, which has no name).
- `fromASM` (`:73-123`): split on one space; `0` and `-1` literal; an inline
  PUSHDATA takes the next two tokens (`toArray(undefined)` an empty push); any
  other non-opcode token a minimal push of its hex (`""` the empty push `00`).

go-sdk@2ca481c holds no such chunk in a script: `NewScriptFromScriptOps`
(`script/script_chunk.go:119-163`) re-encodes every push opcode (`OpDATA1` to
`OpPUSHDATA4`) as `AppendPushData(data)`'s minimal push and writes any other
opcode alone (the data after an `OP_RETURN` appended); `ToASM`
(`script/script.go:190-213`) reads those bytes (`OP_FALSE` for `0x00`,
`opcodes.go:546`). Transcribed in the recorder, not run (no Go toolchain here).

## The rule

`from_chunks` refuses nothing and `to_binary`/`to_asm` write the reference's
bytes and text: the reference's answer, not a stricter one. A chunk whose
opcode and data disagree is not promised to read back, here or in the
reference. No code changes. The two alternatives the issue named are each
pinned against: planted in a scratch copy, `to_asm` writing the ASM of the
serialized bytes turns 3 of the 5 tests RED, `from_chunks` normalizing as
go-sdk's writer does turns 5 of 5 RED.

## Not changed, for the keeper

- `OP_0`/`OP_1NEGATE` written `0`/`-1` (`src/script/chunk.rs`'s `to_asm`); the
  reference writes `OP_0`/`OP_1NEGATE`, go-sdk `OP_FALSE`/`OP_1NEGATE`, and
  go-sdk's `NewFromASM` cannot read `0` or `-1` (`script.go:46-63`, an odd-length
  hex token). A public output of every script holding `OP_0` (`0 OP_RETURN ...`
  data carriers, multisig unlocks), pinned by this crate's own tests
  (`src/transaction/transaction.rs:2365,2393,2538`,
  `tests/script_script_603_b.rs:603`, `tests/script_if_depth_634.rs:292-331`).
- `from_asm`'s empty token: conforming would read `Script::new().to_asm()`
  (`""`) back as `00`, as the reference does; #603 shard A left it to the
  keeper's word.
