# #721: the `ls_identity` parsers' subject choice against the reference

Base `0d8546c0` (`origin/beta`'s tip at the lane's start). The issue, from
#720's rule read (#718): both `ls_identity` parsers pick the transaction of an
identity output's BEEF by `beef.txs.first()`; the reference's discovery reads
another one.

## The reference's choice, by its code

The SDK's `IdentityClient` has no `ls_identity` parser: `resolveByIdentityKey`
and `resolveByAttributes` ask the wallet (`IdentityClient.ts:559-655` at
`ts-stack@edf6e03`), which the toolbox answers through `parseResults` and
`IdentityEvidenceVerifier.parse` (`wallet-toolbox/src/utility/identityUtils.ts:600-612`).
`parse` hands the lookup output (`beef`, `outputIndex`) to
`TransactionEvidenceCoordinator.verify`, whose `parseEvidence`
(`packages/sdk/src/transaction/TransactionEvidence.ts:179-198`) calls
`loadEvidenceTransaction` (`:110-127`):

- `Beef.fromBinaryStrict` (wire order kept, trailing bytes refused);
- `target = beef.atomicTxid ?? beef.txs.at(-1)?.txid` (`:118`): the atomic
  header's subject, else the last transaction on the wire;
- `beef.findAtomicTransaction(target)`, then `outputIndex` checked against that
  transaction's outputs (`:126`).

`decodeIdentityOutput` (`:497-559`) then reads the verified output's locking
script. This is `Transaction.fromBEEF`'s rule too (`Transaction.ts:342-346`,
`txid ?? b.atomicTxid ?? lastTx.txid`), which the SDK's revocation uses
(`IdentityClient.ts:770`), and this crate's `Transaction::from_beef(_, None)`
(`src/transaction/transaction.rs:501-511`), which `revoke.rs:188` already used.
`Beef::from_binary` keeps wire order as the reference's reader does (the sort
happens only when the BEEF is written).

## The three shapes (and two more)

The same two transactions throughout: a proven parent (a lone-leaf BUMP at
offset 0, output 0 `OP_TRUE`) and the subject spending it, output 0 the
reference's own revelation token (#553's `cases[0]`). Every writer (TS 2's and
TS 3's `toBEEF`/`toAtomicBEEF`, this crate's `to_binary`/`to_binary_atomic`)
sorts parents first and the subject last.

| Shape | Reference picks | Crate on the base (`txs.first()`) | Crate after |
|---|---|---|---|
| (a) `single`: the subject alone, proven | the subject | the subject | the subject |
| (b) `atomic_parent_first`: Atomic BEEF, parent then subject (the TS 2 and TS 3 atomic writers' order) | the subject (`atomicTxid`) | the parent: skipped | the subject |
| (c) `parent_first`: BEEF V2, parent then subject (the TS 2 and TS 3 `toBEEF` order) | the subject (the last) | the parent: skipped | the subject |
| `subject_first`: BEEF V2, subject then parent, no header | the parent (the last): skipped | the subject: read | the parent: skipped |
| `atomic_subject_first`: Atomic BEEF, subject then parent | the subject (`atomicTxid`) | the subject | the subject |

So the base skipped a revelation in the two shapes every writer produces once
the token's own transaction is unproven (its BEEF then carries a parent, proven
or not, as the vector's proven parent shows), and read one the reference
skips when a BEEF lists the subject before its parent with no atomic header.

## The fix

Both parsers (`parse_output_to_certificate`,
`parse_output_to_verifiable_certificate` in `src/identity/client.rs`) take the
transaction from `Transaction::from_beef(&output.beef, None)`, the reference's
rule; a BEEF it refuses (no transaction, the atomic subject absent) is a skip,
as `parseEvidence`'s throw is a skip there. The output index is then read on
that transaction, as before.

## Residue

The toolbox's evidence layer is still not ported (#553's stated residue): the
reference verifies the selected transaction's graph and proofs before decoding,
so a BEEF with an incomplete unconfirmed graph refuses the whole discovery
there and is read here. The subject choice no longer differs.
