# Releasing bsv-rs

The beta canary order starts with the toolbox's and CLI's `beta` lines taking
an explicitly pinned bsv-rs beta prerelease. After the CLI's gate passes, the
workers' captains and LOW's captain re-pin on their own trains; the apps'
captains follow the layer they consume. The current pins, feature slices,
owners and dated re-pin proposals live in [docs/DEPENDENTS.md](docs/DEPENDENTS.md).
Each pin-move PR refreshes [docs/dependents.lock](docs/dependents.lock) from the
consumer's remote default branch. Stable requirements do not admit beta
prereleases. This canary paragraph does not authorize a pin, tag, deployment
or release; #100 owns the full release policy.

1. Every change reaches `main` through a pull request; `main` is protected, admins included, linear history.
2. The PR merges (rebase-merge) once its required checks are green: on `beta` five since the small gates were bundled (`docs/lanes/ci-speed-2.md`): `Test Suite (ubuntu-latest, stable)`, `lint` (Rustfmt, Clippy, deny, ratchet as steps), `checks` (mutants-entries, front-pages, vectors, fixtures, front page, secrets, Documentation, wasm32 (combined) as steps), `main-in-beta`, `semver`; on `main` thirteen until the pull request that promotes the bundling to `main` (it runs its merge ref's `ci.yml`, so it reports `lint` and `checks` and never the replaced contexts; `main`'s PATCH to six happens at that pull request, after its run is green and before its merge): `Test Suite (ubuntu-latest, stable)`, `Clippy`, `Rustfmt`, `Documentation`, `vectors`, `deny`, `dependents`, `semver`, `beta-born`, `ratchet`, `fixtures`, `secrets`, `wasm32 (combined)`, then six (`Test Suite (ubuntu-latest, stable)`, `lint`, `checks`, `dependents`, `semver`, `beta-born`). Each gate inside `lint` and `checks` prints its own `PASS`/`FAIL` line and the job's last step names every gate that failed. The captain changes a line's protection with the `checks` form, each context bound to `app_id` 15368, reads it back, and updates the sequencer's required-check list in the same change (`docs/lanes/ci-speed-2.md`, the landing instructions). A pull request and a push to either line run exactly the line's required set and nothing else (a push less `semver` and `beta-born`, which read a pull request); the full test matrix runs on a dispatch of `ci.yml` (the nightly's on each line) and on a tag's call. Separate workflows (`bench.yml`, `msrv.yml`, `features.yml`, `machete.yml`, `docs.yml` for actionlint) run on `workflow_dispatch` and before every tag (step 5), never on a branch push (the owner's word of 2026-10-27). Benchmark comparisons skip tag refs (#515); benchmark builds and the scoreboard still run. A run `ci.yml`'s concurrency rule cancelled is superseded by the newer run of the same ref, never a red.

   From north-star wave 1, `deny` is a required check; the captain adds it to branch protection at landing. The gate (a step of `lint` since the small gates were bundled, `docs/lanes/ci-speed-2.md`) installs the cargo-deny 0.20.2 release binary through `taiki-e/install-action` (checked against the action's manifest; built from its pinned crates.io version until the bundling), resolves one audit lockfile, then checks all features, the Cloudflare wasm32 slice and default features with `--locked`. RustSec findings and yanked crates fail the gate, the advisory ignore list stays empty, licenses are allowlisted, and dependency sources are restricted to crates.io.

3. A release is a PR like any other: bump `version` in `Cargo.toml`, add the `CHANGELOG.md` heading, merge it green. The release commit is `Cargo.toml` and `CHANGELOG.md` alone (step 17; `beta-born` admits nothing else on `main`), so the ledger is not in it, nor the ratchet's lock: `tools/ratchet/library.Cargo.lock` needs no edit for a version, the tool setting the crate's own version in its scratch copy (`docs/RATCHETS.md`, "When a dependency changes"). Before the release pull request is opened, the captain refreshes [docs/DEPENDENTS.md](docs/DEPENDENTS.md)'s pin table by its own pull request on `beta` (each dependent's requirement and resolved version measured at its live tip that day, dated), and the release cites the ledger's date. Before the release pull request is opened, the captain also lists every `### ` heading the new version heading will take, and every entry under each, and checks each against `git diff <last published tag>..<tip>` on the line (the tag of the line's last version crates.io serves, `vX.Y.Z` on `main` and `vX.Y.Z-beta.N` on `beta`: a tag never published, as `v0.8.4`, is not the base, its entries shipping in the next section): an entry can reach a changelog inside a cherry-pick without its code (`c014150e`, a CI pick of 2026-10-26, carried main two #258 entries for code main does not have, and they stood under the `[0.8.4]` heading on 2026-11-10), so each heading names a change the diff shows or it leaves the section. The release commit is rehearsed against every required check of its line before the sitting (a pull request's run of the commit as it will land, draft until the sitting: a push's run lacks `semver` and `beta-born`, which read a pull request; for a security patch of step 23 a public branch may carry nothing of the defect, so there the draft pull request carries the version bump under a heading that names no defect, the entry itself read on the private fork): on 2026-11-10 0.8.4's release commit failed `ratchet` on `main` at its pull request's run, the tool's lock then recording the crate's own version (fixed in the tool, PR #859 on `beta`, PR #860 on `main`). At each prerelease pin and before a minor tag, dispatch the complete mutation run on the line, the figure the release cuts into the record (`gh workflow run nightly.yml --ref <line> -f mode=complete`; every measured file in twenty shards, and the fuzz budget, `docs/NIGHTLY.md`, cut 7): `nightly.yml` is dispatch-only and not callable, so `release.yml` cannot run it; none for a patch. The nights between are incremental (`gh workflow run nightly.yml --ref beta`) and carry every unchanged file's figure from this run. A measurement can be read ahead of the tag by dispatching its workflow on the line (`gh workflow run bench.yml --ref <line>`, and `msrv.yml`, `features.yml`, `machete.yml`, `docs.yml`).
4. Tag the merged commit on `main`: `git tag vX.Y.Z <sha> && git push origin vX.Y.Z` (the tag must equal `Cargo.toml`'s version).
5. The tag runs `.github/workflows/release.yml`: it checks the tag against the manifest and that the commit is on its line, then calls `ci.yml` (the required set, including Documentation, and the whole test matrix) and the five separate workflows (`docs.yml`, `msrv.yml`, `features.yml`, `machete.yml`, `bench.yml`), then `cargo publish --dry-run` and `cargo publish`. The `version` job refuses a tag whose `CHANGELOG.md` has no `## [X.Y.Z]` heading, or an empty one, before anything is published (the page is made from that section). After the publish, the `page` job makes the GitHub Release page (the only job of the workflow holding `contents: write`): `front_pages.py notes <tag> --run <this run>` writes the notes from the tag's own section (one bullet per `### ` heading, every Migration line), the PUBLISHED advisories it fixes or is affected by, and a "Measured at this tag" block read from this run's jobs and logs (an input it cannot read written "not recorded"), the tag's hand-written `docs/releases/<X.Y.Z>.md`, when it has one, placed under the kind line, and `gh release create --verify-tag` (or `gh release edit` when a page for the tag exists, never a second create) takes `front_pages.py flags`'s marks, read into a variable on a line of their own so that a failing `flags` stops the step (`--prerelease` on a `-` version; `--latest` only on the highest stable version, so a back-patch never takes it). Then `front-pages`, the reconciler (`front_pages.py check --wait 3600`), goes red when a front page disagrees with what was published: crates.io's `max_stable_version`, GitHub's Latest and the newest stable `v*` tag differ; a version crates.io serves has no Release page, or a page's prerelease mark is wrong, or a page names a version crates.io lacks; docs.rs did not build the newest stable version or its page lacks a public module of `src/lib.rs`; the README crates.io renders for it names a version before `## Examples` (from 0.8.7 on); `SECURITY.md` is missing on `main` or `beta`; the repository's description is not the manifest's or its homepage not the manifest's `documentation` (its `homepage` for a tag whose manifest has no `documentation`); a page inside a published advisory's range, or the page of a version that fixes one, does not name it. It waits only for what time heals (docs.rs's build, crates.io's index); when only such failures are left after the hour it ends with a warning naming them and exits 0, and a dispatch of `front-pages.yml` looks again later. The five versions crates.io serves with no tag (0.3.20, 0.3.19, 0.3.18, 0.3.0, 0.2.0) are tolerated by name, each with its reason, in `front_pages.py`'s `UNTAGGED`. A red `front-pages` publishes nothing back and writes nothing: the captain fixes the page it names by hand (`front_pages.py notes <tag>` prints its notes) and dispatches `front-pages.yml` until it is green. A page left red by a failed `page` job is made by hand from the same command's output (`gh release create <tag> --verify-tag --notes-file ...` with the `flags` command's marks). The publish waits for `ci.yml`, `docs.yml`, `msrv.yml`, `features.yml` and `machete.yml` (non-blocking inside); `bench.yml` runs beside it and does not hold it. On a tag it runs benchmark builds and the scoreboard, skipping the runner-sensitive regression comparison; dispatch `bench.yml` on a branch to compare. A prerelease tag runs the same.
6. Nothing publishes from a laptop; no crates.io token is stored anywhere, in this repository or its secrets.
7. Publishing uses crates.io trusted publishing: the crate's Trusted Publishing setting names owner `Calhooon`, repository `bsv-rs`, workflow `release.yml`, no environment.
8. A failed release job publishes nothing; fix through a PR, then tag the next patch. Deleting and re-pushing the tag is not available: the repository's ruleset `v* tags: no deletion` forbids it (`gh api repos/Calhooon/bsv-rs/rulesets`). A `v*` tag is not moved either (a second ruleset admits an update by the admin role alone, and `v0.9.0-beta.4` was moved by it twice on 2026-10-30, its release runs at `8623d807`, `0da1886d` and `56d12075`, published from the third; `release.yml` checks only that the tag names the manifest's version and that its commit is on its line, so nothing but this sentence stops a move): a tag whose release run failed or was cancelled stays where it is, its `CHANGELOG.md` section says it was tagged and never published, and why, and the next version number ships (the next patch on `main`, the next `-beta.N` on `beta`, step 14). 0.8.4 is the case: tagged on `main` at `9caa38b4`, its release run cancelled before the publish step because one entry under its heading described code the line does not have (step 3), its section saying so on both lines, and the fix shipped as 0.8.5.
9. A published version is never re-published. A release that is wrong against its predecessor is yanked on crates.io and superseded by the next patch (0.3.21 was); a defect that every published release carries is answered by a patch on the stable line and an advisory, and nothing is yanked, because a yank reaches no lockfile and leaves a build with nothing to resolve to (step 23).
10. Without the trusted-publishing setting on crates.io the publish step fails closed.

## The two lines (2026-10-23, the owner's word: every crate on a beta line)

11. `main` is the stable line: steps 1 to 10 above, unchanged. A quick fix anyone needs lands there as a patch.
12. `beta` is the programme's line (the epic #101; the lane briefs under `docs/lanes/`). It is protected as `main` is (the same required checks, linear history, admins included); CI runs on both lines. A pull request runs exactly its base line's required checks (the jobs `dependents` needs with it) and nothing else; a push to either line runs the same set less the two that read a pull request (`semver`, `beta-born`; the owner's word of 2026-10-27); the sync's dispatch, the nightly's dispatch of `ci.yml` on each line and a tag's call run every job of `ci.yml` and the whole test matrix (2026-10-26; `tests/arch_ci_pr_runs_the_required_set.rs` pins every set against the contexts read from each line's protection, so a context added to or dropped from a protection moves the test with it). Every programme PR targets `beta`, one concern each, reviewed cold before the captain merges.
13. `main`'s commits come back to `beta` after every stable patch, so `beta` never lacks a fix `main` has: the sync PR below (cherry-picks, landed by rebase merge), checked by `main-in-beta`.
14. A prerelease is a tag `vX.Y.Z-beta.N` on `beta`, cut by the owner's word like any tag, with `Cargo.toml` at `X.Y.Z-beta.N` by a PR that says so; `release.yml` admits a `-beta.` tag only on `beta` and a plain tag only on `main`, refuses every other form of tag (`-rc.1`, `-alpha`, a build suffix `+1`) in its `version` job before anything is published (`tests/arch_ci_lines.rs`), and publishes either, after the same calls (step 5: `ci.yml` and the five measurement workflows run on a prerelease tag too). A beta tag is never admitted to the stack's line. When a prerelease carries a fix that a published advisory names, the same sitting adds the prerelease to the advisory's patched versions on GitHub (the advisory's range edited: its prerelease range closed below the patched prerelease and that prerelease named patched); the RustSec file needs no second pull request if the form that names every version after the last affected prerelease under `patched` from the start (`"> X.Y.Z-beta.N"`, step 23 (f)(iv)) is merged there, an open point on `rustsec/advisory-db#3539`; if it is not, a second pull request there adds the patched prerelease (`">= X.Y.Z-beta.N"`) in this sitting. If the minor `X.Y.0` ships before any patched prerelease was added to the advisory's records, the minor's own sitting adds it: `">= X.Y.0"` in the RustSec file's `patched`, and the GitHub advisory's prerelease range closed.
15. Before a prerelease publishes, it is announced to the toolbox's captain and the CLI's captain with the fixtures' diff since the last minor (`docs/FIXTURES.md` once #76 lands). Their beta lines are the canary; the Cloudflare workers and LOW re-pin by their own captains after the CLI's gate has run.
16. `beta` merges into `main` only when the line is god tier (the owner's word of 2026-10-27 17:5xZ, given to the keeper and recorded verbatim on the stack's rulings page: "no merge to main until god tier and 110% confidence nothing breaks and we in conformance with other SDKs and all other sdk issues are logged on their repos"; it binds every crate's main). The gate, the standing definition on epic #101: every scoreboard row at target with recorded evidence and every phase exited; the toolbox's and the CLI's beta lines built against a `vX.Y.0-beta.N` prerelease, the CLI's gate run and the production reads green; conformance with the other SDKs proven, meaning `CLAUDE.md`'s divergence list is empty or every row carries a filing number on the other SDK's repository (ts-stack, go-sdk, py-sdk, the BRCs) or the word "ours" with its reading, no row an unfiled finding against another SDK. Until then the line stays on `beta` through its prereleases, the canaries pin them, and `main` stays the stable minor for the stable consumers. A phase exit is not a merge.

## The direction rule (2026-10-25, the owner's word)

Every fix is born on `beta`. `main` accepts a quick fix of four classes only, and of a fifth, the front pages, once the owner gives his word on it (the last bullet):

- a security advisory (a RustSec entry against this crate or a dependency);
- a panic on input;
- a wrong consensus or BEEF verdict;
- a break in a live dependent (`docs/DEPENDENTS.md`);
- the front pages (the fifth class; the captain's ruling on three design reads of 2026-11-11, on the owner's ask that the README and the versions follow each release; it awaits his word): `README.md`, `SECURITY.md`, `docs/releases/` (a Release page's hand-written notes, landed by their own pull request before the tag), `Cargo.toml`'s `[package]` metadata and `[package.metadata.docs.rs]` (never its `version`, which is the release commit's), the release workflow's page and reconciler jobs (`release.yml`'s `page` and `front-pages`, `front-pages.yml`, `.github/scripts/front_pages.py` with its tests and fixtures), and their tests (`tests/front_page.rs`). A front page is what crates.io, docs.rs and GitHub show for the stable line, so `main` takes each such commit of `beta` by `git cherry-pick -x` (step 17), resolved to what `main`'s tree proves: a sentence whose producer `main` lacks is cut from `main`'s README, `tests/front_page.rs` deciding, and a section of `beta`'s alone stays `beta`'s.

17. Every main commit is `git cherry-pick -x` of a beta commit with its test. The `-x` line, `(cherry picked from commit <sha>)`, is the link both guards read; a pick made without it (a hand-resolved one whose patch differs) fails them until the line is added with `git commit --amend`. The one main-born commit is the release commit (step 3): `Cargo.toml`'s `version` and `CHANGELOG.md`'s headings, nothing else.
18. `main-in-beta` (`.github/workflows/ci.yml`) runs on every PR into `beta` (on the PR's merge commit: after this lands, does beta carry main), every push to `beta`, and a dispatch on `sync/main-into-beta`. A commit of `origin/main` is on the tree by sha, by patch (`git cherry`), or by a cherry-pick link in either direction: main's commit names a beta source on the tree, or a commit of the tree names main's. It fails naming each commit that is none of these. `beta-born`, on every PR into `main`, asks the same of each commit of the PR against `origin/beta`, and lets a release commit through, saying so in its log.
19. `.github/workflows/sync-main-into-beta.yml` runs on every push to `main`. When `main-in-beta`'s filter finds commits of main beta lacks, it opens, or updates in place, one PR from `sync/main-into-beta` into `beta`, titled `sync: main into beta at <sha>`: each such commit `git cherry-pick -x`'d onto beta's tip in main's order. **Land it by rebase merge**: both lines keep linear history, and each pick's `-x` line lives in its message, so the link survives the new sha. A pick that conflicts is aborted; the branch keeps beta's tip and the picks before it, the PR names the commit and its conflicted files and carries the label `needs-hand` (the workflow creates the label; it holds `issues: write` for that). Resolve on the branch by `git cherry-pick -x <sha>`, push, and run `gh workflow run sync-main-into-beta.yml`: a branch that holds beta's tip is picked onto, never rebuilt, so a hand resolution survives main moving again; when beta moves, the branch's own commits are carried onto its tip. A release commit that picks cleanly is labelled `needs-hand` too: its pick moves beta's `[Unreleased]` under main's heading, so a person amends it to what beta should say before it lands. A conflicting commit with no pick before it opens no PR (GitHub opens none without a commit): the run fails with the hand's steps in its summary.
20. A PR or a push made with the `GITHUB_TOKEN` starts no workflow, so the sync workflow starts `ci.yml` on its branch by a `workflow_dispatch`; the required checks report on the branch's tip from that run. The protection the captain adds: `main-in-beta` a required check on `beta`, `beta-born` on `main`; linear history stays on both lines.
21. A change to `main`'s own gate (`ci.yml`'s jobs on `main`, `docs/RELEASING.md`'s words on them) is the one class of main commit with no beta source, and the guards do not know it: a captain links it back by a commit on `beta` that carries each main commit's `(cherry picked from commit <sha>)` line, under a PR like any other. The link commit has content (this point was its first); GitHub's rebase merge and `gh pr update-branch --rebase` drop an empty commit, and a PR of empty commits closes itself when its branch is updated (PR #224, 2026-10-25). Run the guard's shell by hand on the line's tip before it is required (`main-in-beta` on `beta` was required while `main` held five unlinked gate commits, and every open beta PR was held until the link landed).
22. A job permission added to `ci.yml` (or to any workflow `release.yml` calls) must stay within what `release.yml` grants that call (`permissions: contents: read` on every `uses:` job): GitHub refuses a called workflow whose permissions exceed the caller's, and the tag's run then dies at startup with "a workflow file issue" before any job runs (the toolbox's `v0.14.0-beta.2` on 2026-10-28, its semver job's `pull-requests: read`; nothing published until the fix landed and the tag moved). Read `release.yml`'s grants before adding a permission to a job.
23. A security patch on the stable line (the security-advisory class above; `SECURITY.md`; root rule 12; the path #840 takes, `docs/design/843-identity-and-framing.md` section 6). A finding of rule 12's class is worked off the public repository until its patch can be released in the same sitting (the two public CI runs, on `beta`'s pull request and on `main`'s, are part of the sitting), in this order. A draft security advisory is opened on this repository's Security tab before anything else, and nothing of the defect goes to an issue, a pull request, a public branch, a commit message on one or a lane record while a published line carries it. (a) A lane builds the fix, with the test that was RED before it, on a branch from `beta` that is never pushed to this repository: it is pushed to the advisory's temporary private fork, which runs no Actions, so the lane's own whole gate on the box and the three reads are the proof. (b) A port of the same patch onto a branch from `main` is prepared on the same fork and read there too, with the test shown RED on `main`'s tip before it and green after, so that nothing is designed in public; the release commit (step 17's one main-born commit, step 3) is prepared beside it, and the ledger is refreshed by step 3's own pull request on `beta` before the sitting (it carries pins alone, nothing of the defect). (c) When the release can follow in the same sitting, the fix lands on `beta` by its public pull request; the rebase merge gives it its `beta` sha. (d) The `main` pull request is the `git cherry-pick -x` (step 17) of that `beta` commit: the same patch the reads judged in (b), re-made mechanically so that its `-x` line names a commit `beta` carries (`beta-born` admits a commit by its patch or by that line and never compares the pick with (b)'s branch, so the captain diffs the two before the pull request is opened), with the release commit; its public CI run is the release's, and a red check holds the publication. (e) The tag (step 4) and `release.yml` (step 5). (f) In the same sitting, once crates.io has the version, the advisory published, with the affected range and the patched versions, and then `gh workflow run front-pages.yml --ref main`, the sitting ending when it is green (every Release page inside the advisory's range names it, and the page of the version that fixes it names it under Fixes: `front_pages.py notes <tag>` prints the lines to add by hand; the patched release's page was made before the advisory was public, so its Advisories lines are added the same way). A security patch's hand notes cannot be public before its fix: no `docs/releases/<X.Y.Z>.md` lands before the tag, `release.yml`'s `page` job makes the page without it (one `::warning::` line saying the tag has none, the step going on), and once the advisory is published the sitting lands the file on `beta` and rebuilds the page from it with `python3 -B .github/scripts/front_pages.py notes vX.Y.Z --run <the release run's id> --hand docs/releases/X.Y.Z.md > notes.md` and `gh release edit vX.Y.Z --notes-file notes.md` (the script's options are `notes <tag> [--run <id>] [--hand <file>]`, `flags <tag>`, `check [--wait <seconds>] [--readme-from <version>]`, and `--offline <dir>` on each) (the patch, and the next beta prerelease that carries the fix when it is published, step 14), a CVE requested and a RustSec entry filed from it; nothing yanked where every published release carries the defect (step 9's sentence). What 0.8.5's advisory (GHSA-j8hr-pjhm-6h27, 2026-11-10) taught, each a duty of the sitting: (i) every public sentence of the sitting that says what a version does (the advisory's, the release's `CHANGELOG.md` section, `SECURITY.md`'s row, the tracker's comment, the pull request bodies, the notes to dependents, and what a private report says of this crate), each end of each range, and every leg of the workaround is RUN on the crates as crates.io serves them, each leg on the defect's own input on an affected version and seen to catch it, and on an honest input and seen to pass (the last affected stable, the oldest version that has each named function, the prerelease ends, and a sweep of every published version for the ranges), the affected side before the sitting and the patched side once the index shows the patch (a `cargo` resolution of `=X.Y.Z` in a scratch project with no lockfile succeeds) and before the advisory's `state=published`, the advisory staying a draft until that run returns (0.8.5's was corrected three times after publication: a workaround leg that always passed on an affected version; then a sentence partly wrong, a sentence false and six omissions, the advisory's own count in its corrections section; all found by running them; its correction note's count was then reworded once, at 21:42Z); (ii) the score is CVSS 3.1 for the library's reasonable worst-case use (the CVSS 3.1 user guide, section 3.7), the assumption written in the advisory, the vector put to independent reads (root rule 13) before publication (0.8.5's was raised from 5.9 to 7.5 after them, the original score having counted the adopting application's design as an attack condition); (iii) where another implementation shares the flaw, its private report is sent and read back BEFORE this advisory is published and before any public line here states that implementation's behaviour; (iv) the RustSec files. What RustSec's reviewer asked on `rustsec/advisory-db#3539` (2026-11-11): one problem per advisory, so a GitHub advisory that covers two problems is two RustSec files, each with its own functions, title and CVSS vector and each with the GHSA id in `aliases` (several drafts in one pull request are named `crates/bsv-rs/RUSTSEC-0000-0000.<slug>.md`, the reviewers assigning the ids); that the versions after 0.9.0-beta.7 be treated as unaffected; the text short (a paragraph of what the defect is, the fixed version and a one-line workaround; no Patches or Workarounds sections); the description following their pull request template. What this project found by its own runs, not the reviewer's words: the `url` may not be the GitHub advisory's when its id is in `aliases` (the changelog at the tag serves); rustsec orders versions and does not read a `VersionReq`, so the stable range's `patched` is bounded above by the line's earliest prerelease (`">= 0.8.5, < 0.9.0-beta.1"`), or the affected prereleases read as patched. Our answer to the reviewer's unaffected point is to put the versions after the last affected prerelease under `patched` at once (`"> 0.9.0-beta.7"`: the fix is on `beta`, from which every later version is cut), an open point on `rustsec/advisory-db#3539` when this line was written: if that form is merged there, no second pull request is owed when a patched prerelease publishes (step 14), and if it is not, the form they ask for is followed and step 14's second pull request is owed. Run their linter (`rustsec-admin lint`) and their range code (`Versions::is_vulnerable`) on each file before the pull request; (v) a correction after publication is dated inside the advisory, in a section of its own, the time beside each. (g) The dependents are crates.io's reverse-dependency list that day (`https://crates.io/api/v1/crates/bsv-rs/reverse_dependencies`), not memory, with each one's newest version and its requirement (the ledger as step 3 refreshed it, `docs/DEPENDENTS.md`); those whose requirement does not admit the patch (an exact pin, an older minor) are told by name, with the pin edit each needs; a dependent deployed from a branch and never published is on no such list, so every row of `docs/DEPENDENTS.md`'s Rust consumers table that the list lacks is told by its keeper the same way; each one's published source is read for whether outside bytes reach the flaw, and what is found goes to that crate's keeper privately, never to an issue. (h) The sync pull request carries the release commit back to `beta` (step 19).
